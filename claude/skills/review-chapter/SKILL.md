# 챕터 내용 검증 및 편집 마감 점검

## 역할

Node.js Deep Dive 책의 챕터를 검증하는 기술 에디터다. 다섯 가지 점검으로 나뉜다.

1. **사실 검증** — 공식 문서 기반의 기술적 정확성 확인 (기본)
2. **편집 마감 점검** — 출간 직전 일관성·연결성 검사 (`polish`)
3. **챕터 간 정합성 스윕** — 다른 챕터와의 상호 참조·서술 충돌 검사 (`consistency`)
4. **적대적 독자 리뷰** — 시니어 독자 관점의 논증·방법론 공격 (`adversarial`)
5. **실전 퀴즈 검증** — 퀴즈의 풀이 가능성과 정답 타당성 검사 (`quiz`)

## args 해석

- `{파일 경로 또는 챕터 번호}` — 사실 검증만 실행 (기본)
- `{파일 경로 또는 챕터 번호} polish` — 사실 검증 + 편집 마감 점검
- `{파일 경로 또는 챕터 번호} polish-only` — 편집 마감 점검만 실행 (사실 검증 생략)
- `{파일 경로 또는 챕터 번호} consistency` — 챕터 간 정합성 스윕만 실행
- `{파일 경로 또는 챕터 번호} adversarial` — 적대적 독자 리뷰만 실행
- `{파일 경로 또는 챕터 번호} quiz` — 실전 퀴즈 검증만 실행
- `{파일 경로 또는 챕터 번호} full` — 다섯 가지 전부 실행
- 키워드는 병기할 수 있다 (예: `6.2 quiz adversarial` → 두 점검만 실행)
- args가 없으면 사용자에게 어떤 파일을 검토할지 묻는다

챕터 번호(예: `1.3`)만 받으면 `posts/part{N}/{N.M}.*.md` 패턴으로 파일을 찾는다.

> **공통 원칙: sub-agent에 위임하지 않는다.** 어떤 점검이든 본문 읽기, grep/WebFetch, 결과 정리를 메인 대화에서 직접 수행한다. 검증 과정과 원문 인용이 transcript에 남아야 사용자가 결과를 신뢰할 수 있다.

## Part 1: 사실 검증 (기본 단계)

### 1단계: 파일 읽기

args로 받은 경로/번호로 파일을 Read한다. 파일이 크면 offset/limit으로 나눠 읽되 *전체 본문을 한 번씩 훑는다*.

> **반드시 직접 읽을 것.** 이 스킬은 sub-agent(`Agent` 도구)에 위임하지 않는다. 챕터 본문 읽기, WebFetch/WebSearch를 통한 공식 문서 대조, 결과 정리까지 *모든 단계*를 메인 대화에서 직접 수행한다. 여러 챕터를 한 번에 검토하라는 요청이 들어와도 챕터를 sub-agent에 분담시키지 말고 순차적으로 직접 처리한다. 이유는 (1) 검증 과정의 모든 WebFetch 호출과 원문 인용이 transcript에 남아야 사용자가 신뢰할 수 있고, (2) sub-agent의 보고를 그대로 옮기면 검증의 깊이와 책 톤·집필 원칙(`CLAUDE.md`, `GUIDE.md`)의 적용을 보장하기 어렵기 때문이다.

### 2단계: 기술적 주장 추출

파일 전체를 읽으며 다음 유형의 주장을 전부 목록으로 정리한다. 코드 예제는 제외하고 텍스트 주장만 대상으로 한다.

- **API/동작 설명**: "`fs.readFile()`은 libuv 스레드 풀을 사용한다"
- **내부 메커니즘**: "V8은 히든 클래스를 생성한다", "epoll은 엣지 트리거로 동작한다"
- **구체적 수치**: "기본 스레드 풀 크기는 4개", "힙 제한은 1.5GB", "4배 빠르다"
- **버전 주장**: "Node.js 22부터 지원", "Node.js 24에서 추가된"
- **비교 주장**: "cluster보다 Worker Threads가 메모리를 덜 사용한다"

### 3단계: 유형별 검증

각 주장을 아래 전략으로 검증한다. **검증은 병렬로 최대한 빠르게 진행한다.**

**구체적 수치 — 즉시 플래그, 조회 없음**
- 각주가 없으면 → ⚠️ 플래그 (조회 불필요, 출처 자체가 없으므로)
- 각주가 있으면 → 해당 URL WebFetch로 원문과 수치 일치 여부 확인

**API/동작 설명**
- WebFetch로 `https://nodejs.org/docs/latest/api/` 해당 섹션 직접 확인
- 문서에 없거나 다르면 → ❌

**V8 내부 메커니즘**
- WebSearch로 `site:v8.dev {키워드}` 검색 후 관련 글 WebFetch로 확인

**libuv 관련**
- WebFetch로 `http://docs.libuv.org/en/v1.x/` 확인

**버전 주장**
- WebFetch로 `https://nodejs.org/en/blog/release/` 릴리즈 노트 확인

**공식 문서로 검증 불가한 내용**
- 소스코드 수준의 구현 세부사항 등 → 🔍 표시

## Part 2: 편집 마감 점검 (`polish` 인자 포함 시)

사실 검증과 다른 결의 점검이다. 외부 출처 조회 없이 *파일 내부 일관성* 과 *연결성* 을 확인한다.

### 5단계: 자동 점검 (Bash 일괄 실행)

5개 항목을 Bash로 일괄 점검한다. 가능하면 병렬로 실행한다.

#### 5.1 본문 수치 vs 실측값 일치

본문에서 *"N배 빠르다", "N% 감소", "Nms 걸렸다"* 처럼 단언한 수치가 같은 파일 안의 *측정 결과 블록* 출력값과 일치하는지 확인.

```bash
/usr/bin/grep -nE "([0-9]+(\.[0-9]+)?)(배|%|ms[^=]|ms$|초)" {파일경로} | /usr/bin/head -100
```

- 본문 주장(단언) vs 측정 결과 블록(실측)을 *수치 단위로* 매칭
- *반올림 차이* 는 허용 (예: 11.976ms → "12ms")
- 어긋나면 → 본문 수치를 실측치에 맞춰 수정하거나, 본문을 정성적 표현으로 완화

#### 5.2 각주 번호 일관성

본문 참조 `[^N]` 와 각주 정의 `[^N]:` 가 1:1로 매칭되는지, 임시 번호(`[^Nb]`, `[^Nx]`)가 남아있지 않은지 확인.

```bash
echo "[본문 참조]"; /usr/bin/grep -oE "\[\^[0-9a-z]+\]" {파일경로} | /usr/bin/grep -v ":$" | /usr/bin/sort -u
echo "[각주 정의]"; /usr/bin/grep -nE "^\[\^[^]]+\]:" {파일경로}
```

- 임시 번호 발견 시 → 정수 번호로 재정렬 (URL이 중복이면 기존 각주에 통합)
- 본문에 참조 없는 각주 정의는 *불필요한 각주* 로 표시

#### 5.3 코드 블록 언어 명시

` ``` ` 만 있고 언어가 명시되지 않은 코드 블록 시작 위치를 찾는다.

```bash
/usr/bin/awk '
  /^```/ {
    if (in_block) { in_block = 0 } else {
      in_block = 1; lang = $0; gsub(/^```/, "", lang)
      if (lang == "") print "  L"NR": [언어 없음]"
    }
  }
' {파일경로}
```

- 언어 없는 블록 발견 시 → 가장 가까운 적절한 언어(보통 `text`, `bash`, `javascript`) 명시

#### 5.4 예제 파일 경로 존재

본문에서 참조하는 `examples/...` 경로가 *실제 파일* 인지 확인.

```bash
/usr/bin/grep -ohE 'examples/[A-Za-z0-9./_-]+\.(js|mjs|cjs|ts)' {파일경로} | /usr/bin/sort -u > /tmp/refs.txt
while IFS= read -r path; do
  [ -f "$path" ] || echo "❌ 누락: $path"
done < /tmp/refs.txt
```

- 누락 파일 발견 시 → 예제 파일을 실제로 생성하거나, 본문에서 해당 참조를 제거

#### 5.5 외부 링크 생존

각주의 외부 URL이 HTTP 200/301/302를 반환하는지 일괄 점검. *시간이 오래 걸리므로 마지막에 실행*.

```bash
/usr/bin/grep -ohE 'https?://[^ )>]+' {파일경로} | /usr/bin/sed 's/[.,)>;]*$//' | /usr/bin/sort -u > /tmp/links.txt
while IFS= read -r url; do
  code=$(curl -sILo /dev/null -w "%{http_code}" --max-time 8 -A "Mozilla/5.0" "$url")
  case "$code" in
    200|301|302) ;;
    *) echo "[$code] $url" ;;
  esac
done < /tmp/links.txt
```

- 4xx/5xx 발견 시 → 브라우저로 한 번 더 확인(curl 403은 봇 차단일 수 있음)하고, 실제 죽었으면 대체 URL 또는 Wayback Machine 링크로 교체

### 6단계: 수동 점검 (사람 눈)

자동화로 못 잡는 *문맥 의존* 일관성을 확인한다.

#### 6.1 "이 절에서 기억할 것" 박스 형식

박스 9개 이상이 있으면 모두 추출해서 비교한다.

```bash
/usr/bin/awk '
  /이 절에서 기억할 것/ { in_box=1; start=NR; lines=0; next }
  in_box && /^>/ { lines++; next }
  in_box && !/^>/ { in_box=0; print "  → "lines"줄, L"start"-L"(NR-1) }
' {파일경로}
```

- 박스 *형식*(줄 수, 항목 수, 글머리표) 통일성 확인
- 박스 *배치 빈도* 가 챕터마다 달라도 *디자인 결정* 으로 보고 강제하지 않음
- 단, 박스 안의 *항목 길이* 가 들쭉날쭉(1줄짜리 옆에 5줄짜리)이면 ⚠️ 표시

#### 6.2 cross-reference 표기 통일

*"X.Y장에서", "X.Y.Z절에서", "X.Y.Z 참고"* 같은 표기 변형을 확인.

```bash
/usr/bin/grep -nE '[0-9]+\.[0-9]+\.[0-9]+(\.[0-9]+)*[ 에을는이가]' {파일경로} | /usr/bin/grep -vE '^[[:space:]]*##|예제 [0-9]'
```

- *"X.Y.Z" 다음에 "절" 누락* 자리만 통일 대상 (가장 흔한 변형)
- *"확인했듯이", "다뤘듯이", "살펴봤듯이"* 같은 자연어 동사 변형은 *톤 다양성으로 유지*, 강제 통일 금지

## Part 3: 챕터 간 정합성 스윕 (`consistency` 인자 포함 시)

대상 챕터와 *책의 나머지 부분* 사이의 정합성을 검사한다. Part 1·2가 파일 하나를 보는 것과 달리, 여기서는 상호 참조와 공유 개념이 책 전체에서 어긋나지 않는지 본다. 외부 출처 조회는 하지 않는다.

### 8단계: 참조 수집

대상 챕터가 `{N.M}`이라 할 때, 두 방향의 참조를 grep으로 수집한다.

```bash
# outbound: 대상 챕터 → 다른 챕터 (버전 번호·CVSS 같은 오탐을 줄이는 가드 패턴)
/usr/bin/grep -noP '(?<![0-9A-Za-z.])[0-9]+\.[0-9]+(?![0-9])[^,)|]{0,30}' {파일경로} | /usr/bin/grep -vP '^\d+:{N}\.{M}'

# inbound: 다른 챕터 → 대상 챕터
/usr/bin/grep -rnoP '(?<![0-9A-Za-z.]){N}\.{M}(?![0-9])[^,)|]{0,30}' posts --include='*.md' | /usr/bin/grep -v '{대상 파일명}'
```

수집한 매치에서 버전 번호(Node.js 8.5.0), CVSS 점수, 측정치(8.7 MiB), 날짜 등 챕터 참조가 아닌 것을 문맥으로 걸러낸다. **번호만 보지 말고 주변 주제어와 함께 판정한다** (예: "8.4(async_hooks)"처럼 번호-주제 쌍이 현행 목차와 일치하는지).

### 9단계: outbound 참조 검증

대상 챕터가 다른 챕터를 가리키는 각 참조에 대해 확인한다.

- **존재**: 참조된 절 번호(`X.Y.Z`)가 대상 파일의 헤딩으로 실제 존재하는가 (`grep '^#.* X\.Y\.Z' 대상파일`)
- **약속 이행**: "X장에서 다룬다/다뤘다"가 가리키는 내용이 실제로 그 챕터에 있는가 — 대상 파일을 열어 해당 주제의 절을 확인한다
- **주제 일치**: 참조 문맥의 주제어가 대상 챕터의 실제 주제와 일치하는가 (재번호 후 어긋난 참조가 가장 흔한 사례)

### 10단계: inbound 참조 검증

다른 챕터가 대상 챕터를 *설명하는 문구* 가 현재 내용과 일치하는지 확인한다. 다른 챕터가 "N.M장에서 ~를 다룬다"라고 소개했는데 대상 챕터가 개정되어 그 내용이 빠졌다면 어긋남이다. `posts/part0/0.2.*`(학습 가이드)의 파트 지도·전제·추천 경로 설명은 반드시 포함해서 대조한다.

### 11단계: 공유 개념 충돌 검사

대상 챕터가 *정의하거나 수치를 제시하는 핵심 개념* 을 3~7개 뽑아, 같은 개념을 설명하는 다른 챕터를 grep으로 찾아 서술을 대조한다.

```bash
/usr/bin/grep -rln '{개념 키워드}' posts --include='*.md' | /usr/bin/grep -v '{대상 파일명}'
```

- 대조 대상: **단위**(나노초 vs 밀리초), **버전**(도입·안정화·기본값 전환), **수치**(기본값, 한도), **메커니즘 설명**(같은 동작을 다르게 설명)
- 실제 사례: `monitorEventLoopDelay` 히스토그램 단위를 한 챕터는 "밀리초", 다른 챕터는 "나노초"로 서술 → 한쪽이 틀렸다 (이 유형이 이 단계의 주 타깃)
- 어느 쪽이 맞는지는 공식 문서 기준으로 판단하되, 필요하면 Part 1 방식의 WebFetch를 1~2회 허용한다

## Part 4: 적대적 독자 리뷰 (`adversarial` 인자 포함 시)

사실 검증과 정반대 결의 점검이다. Part 1이 "출처와 일치하는가"를 본다면, 여기서는 **출처와 일치하더라도 공격 가능한 논증** 을 찾는다. 페르소나는 이 책의 대상 독자 상한선인 *깐깐한 시니어 Node.js 개발자* 다. 목표는 트집이 아니라, 독자가 신뢰를 거두게 될 지점을 출간 전에 찾는 것이다.

### 13단계: 공격 축 4개로 본문 훑기

챕터 전체를 읽으며 다음 축으로 공격을 시도한다.

**축 1 — 벤치마크·측정 방법론**
- 비교 조건이 공정한가 (한쪽에만 유리한 설정, 워밍업 차이, 단일 실행 vs 분포)
- 측정 결과가 결론을 *실제로* 지지하는가 (측정은 A인데 결론은 A보다 넓은 일반화)
- 이 책 8.1장(벤치마크 방법론)이 세운 기준을 본 챕터의 측정이 스스로 지키는가
- 수치 차이를 특정 원인으로 단정할 때, 대안 설명(측정 변동, JIT, 캐시)이 배제되었는가

**축 2 — 논증 구멍**
- "항상", "절대", "모든", "반드시" 단정에 반례가 존재하는가
- 인과 주장("X 때문에 Y")에서 X 없이도 Y가 가능한가
- 생략된 전제가 있는가 (특정 OS/배포 환경에서만 성립하는 주장을 일반화)

**축 3 — 트레이드오프 누락**
- 권장 패턴의 비용·한계가 언급되는가 (예: "스트리밍 파서를 써라" → 복잡도·에러 처리 비용은?)
- 안티패턴으로 규정한 코드가 *정당한* 사용처를 갖는 경우는 없는가

**축 4 — 독자 수준 비약**
- 0.3장이 선언한 전제 지식 기준에서 따라올 수 없는 비약이 있는가
- 반대로, 전제 지식으로 선언된 내용을 장황하게 재설명하는 곳이 있는가

## Part 5: 실전 퀴즈 검증 (`quiz` 인자 포함 시)

챕터 말미의 실전 퀴즈가 *독자 입장에서 작동하는지* 검사한다. 핵심 절차는 **정답을 보기 전에 직접 푸는 것** 이다. 정답을 먼저 읽으면 풀이 가능성 판단이 오염된다.

### 15단계: 선풀이

1. 퀴즈 *문제와 코드만* 읽는다. **정답 해설은 아직 읽지 않는다** (Read의 offset/limit으로 정답 부분을 의도적으로 제외하고 읽는 것을 권장)
2. 챕터 본문에서 배운 내용만으로 답을 작성한다. 풀이에 사용한 절 번호를 기록한다
3. 본문 밖 지식이 필요했다면 그 지점을 기록한다

### 16단계: 대조와 판정

자기 풀이를 정답 해설과 비교하고, 퀴즈마다 다섯 항목을 판정한다.

| 항목 | 질문 |
|---|---|
| 풀이 가능성 | 챕터 본문만으로 풀리는가? 필요한 절이 모두 본문에 있는가? |
| 정답 정확성 | 해설의 기술적 설명이 옳은가? (의심되면 Part 1 방식으로 1~2회 WebFetch 허용) |
| 누락된 경우의 수 | 해설 외에 정답이 될 수 있는 대안 원인/해법이 있는가? |
| 증상 재현성 | 문제 코드가 정말 그 증상을 내는가? (코드를 논리적으로 추적, 실행까지는 불요) |
| 해법 유효성 | 해설의 수정 코드가 문제를 실제로 해결하는가? 새 문제를 만들지는 않는가? |

### 퀴즈 검증 원칙

- **선풀이 후대조** 가 이 점검의 전부다. 정답부터 읽고 역산하면 "풀 수 있어 보인다"는 착각만 남는다
- 풀이 불가 판정 시, 퀴즈를 쉽게 만들라는 뜻이 아니다 — 본문 보강 위치를 제안하거나, 퀴즈가 의도적 확장 문제라면 "본문 + 힌트 추가"를 제안한다
- 증상 재현성·해법 유효성은 코드 논리 추적으로 판단하고, 실행이 꼭 필요한 의심점은 실행 검증 트랙(별도)으로 넘긴다고 명시한다
