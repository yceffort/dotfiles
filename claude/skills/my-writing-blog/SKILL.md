# 블로그 톤 글쓰기

블로그 게시용 톤으로 한국어 글을 쓴다. 새 글 작성(생성 모드)과 기존 초안 변환(변환 모드)을 모두 지원한다.

**공통 규칙**: 전역 `my-writing` 스킬(한국어 표현 점검·em dash 금지)을 항상 함께 적용한다. 이 스킬은 blog 톤 고유 규칙만 담는다.

## args

- `{주제 또는 파일경로}` — 입력이 **주제/개요 텍스트**면 생성 모드, **`.md` 파일 경로**면 변환 모드. 모호하면 어느 쪽인지 묻는다.

생성 모드의 기본 동작은 **개요 합의 후 작성**, 변환 모드의 기본은 **dry-run 샘플 후 승인**이다. 사용자 승인 전까지 전체를 쏟아내지 않는다.

---

## 문체

> **2026-07 문체 전환**: 기존의 단정·직설 톤이 거만하게 읽힌다는 사용자 피드백으로 **겸손한 설명형**으로 전환했다. 2026-07 이전 글은 옛 톤이므로, 보정 소스로 읽을 때 리듬 차이에 주의한다.

- **종결어미**: `~다` 평어체. 차분한 설명형 리듬을 유지한다. 판정 선고형 단문("React가 이겼다.", "둘은 같은 사건이 아니다.")을 연달아 끊지 말고, 문장을 풀어서 쓴다.
- **단정 완화**: 의견·전망은 "~라고 생각한다", "~일 가능성이 높다", "~일 것이다" 수준으로 여지를 남긴다. 검증된 사실은 단정해도 된다. 확신의 근거가 본문에 있을 때만 세게 쓴다.
- **명령·권유형 지양**: "~보자", "기억해 두자", "갈라야 한다" 같은 독자 지시형 대신 "~를 보면", "~는 뒤에서 다시 나온다", "~할 필요가 있다"로 쓴다.
- **승부·도발 어휘 지양**: "판돈", "두들긴다", "선고", "완패" 같은 관용구와 냉소("훈훈한 이야기다")를 피한다. 위트는 절제하고, 겸손하되 비굴하지 않게.
- **서론**: 정의·배경으로 시작하지 않는다. **구체적 증상·사실·수치로 즉시 진입**한다. (예: "막상 쓰면 직관이 자꾸 빗나간다. DB 쿼리를 감쌌는데 쿼리는 여전히 두 번 나가고…")
- **고정 구조 금지** (2026-08-15 사용자 피드백): "먼저 결론" 절, "정리" 절 같은 정형 스캐폴드를 글마다 기계적으로 반복하지 않는다. 구조는 글의 성격에 맞게 그때그때 설계한다. 긴 글에 요약이 필요하면 서론 산문에 녹이거나 그 글에 맞는 자연스러운 제목·형태로 담고, 마무리도 볼드 키워드 불릿 틀 대신 산문 등 글에 맞는 방식을 택한다.
- **정직한 트레이드오프**: 과장하지 않는다. 반론과 자기 논거의 한계를 명시한다. ("~라는 것이 정직한 평가일 것이다")
- **용어 풀이**: 처음 나오는 개념은 괄호로 짧게 푼다. (예: "빌림 검사기(borrow checker, 참조의 소유권과 수명을 컴파일 타임에 강제하는 장치)")

## 형식

- **em dash(—) 금지** — 상세 규칙은 전역 `my-writing` 스킬 참고. 코드 주석·각주·인용 원제까지 전수 제거하고 `grep '—'`로 0개를 확인한다.
- **마크다운 링크 허용**. `[텍스트](경로)` 형태로 본문에 직접 건다.
- **헤딩 번호 없음**. `## 서론`, `## 먼저 결론`처럼 자유로운 제목.
- **분량 자유**. 하한 없음.
- `>` 인용구로 측정 환경, "한 문장으로:" 요약, 노트를 단다.
- 비교는 표로 정리하고, 키워드는 볼드로 강조한다.
- **요약 불릿을 쓰게 되는 경우**, 앞에 리드인 한 줄과 뒤에 마무리 한 줄을 두고, **불릿은 길이·구조를 일부러 들쭉날쭉하게** 둔다. 모든 항목을 "굵게 + 부연 + 짧은 마무리" 같은 동일 틀로 4개 찍어내면 AI 티가 난다.
- **"다룰 내용"·"목차" 같은 불릿 로드맵 절을 만들지 않는다.** 실제 글엔 없는 전형적 AI 패턴이다. 개요가 필요하면 서론 산문 안에 한 문장으로 녹인다.

## 근거

- 소스 코드는 직접 인용하고 **버전 태그를 고정**한다 (예: `v19.2.6` 태그). `main`은 인용하지 않는다.
- 측정값은 환경(머신, 버전, 도구)을 명시한다. 가상 수치·과장 성과 금지.
- 인용한 소스는 실제 파일과 대조해 확인한다.
- 소스 딥다이브 글은 **서론에 버전·범위 고지 `>` 블록**(고정 태그, 분석 시점)과 각주(`[^n]`)를 두고, 본문엔 파일명·식별자(예: `ReactCacheImpl.js`, `ReactSharedInternals.A`)를 구체적으로 박는다. "명세와 구현을 본다"는 선언만으로는 부족하다.

## 주제 선정 (생성 모드)

**"검색하면 바로 나오는 글"이 아니라 "이 글을 참고해야 답할 수 있는 글"**을 쓴다. "X vs Y" 비교글, "N가지 방법" 나열형, "~란 무엇인가" 단순 설명형은 피한다. 직접 해본 경험(성능 분석, 마이그레이션, 장애 분석), 프레임워크 내부 딥다이브, 실무 레퍼런스가 강점이다.

## 톤 예시 (이 리듬을 목표로 한다)

증상으로 여는 서론:

> `cache()`는 React 19에 정식 추가된 API다. 그런데 막상 쓰면 직관이 자꾸 빗나간다. DB 쿼리를 감쌌는데 쿼리는 여전히 두 번 나가고, 같은 코드를 클라이언트 컴포넌트로 옮겼더니 아무 일도 일어나지 않고, 인자를 객체로 바꿨더니 캐시가 통째로 안 먹는다.

단정을 완화한 의견 제시 (2026-07 이후 톤):

> 여기까지는 충분히 있을 법한 이야기다. 다만 한 가지 짚고 싶은 부분이 있다. 이 시나리오는 인과의 마지막 고리를 생략하고 있다. 검증은 읽을 수 있는 대상에만 가능하다. 낯선 스택으로 작성된 코드는 검수가 어려운 블랙박스가 되기 쉽고, 그런 코드를 책임지고 승인하기는 어렵다. 그래서 결국 자신이 읽을 수 있는 익숙한 스택을 선택하게 될 가능성이 높다.

구체적 현상으로 말하되, 판정을 선고하는 대신 근거를 펼쳐 놓고 결론은 "~할 가능성이 높다" 수준으로 닫는다.

## frontmatter (새 글 생성 시)

```yaml
---
title: '...'
tags:
  - ...
published: true
date: YYYY-MM-DD HH:MM:00
description: '...'
thumbnail: /thumbnails/YYYY/MM/{slug}.png
---
```

날짜는 사용자에게 확인하거나 오늘 날짜를 쓴다. 저장 경로는 사용자에게 확인한다.

## 톤 보정 (저장소가 로컬에 있을 때만)

`~/private/blog/`가 존재하면 최근 글(`apps/blog/posts/*/*/*.md`, `.en.md` 제외)의 서론을 읽어 리듬을 보정하고, `CLAUDE.md`의 주제 전략을 참고한다. 2026-07 이전 글은 옛 톤이므로 주의한다. **없으면 위 명문화된 가이드만으로 진행한다.**

## 워크플로우

**입력 전제**: "직접 해봤다"류의 경험·실측 데이터는 AI가 만들 수 없다. 측정값·장애 경험·벤치마크가 필요한 글이면 **사용자가 제공한 데이터를 입력으로 받는다.** 없으면 그 자리를 지어내지 말고 비워둔 채 `[측정값 필요]`로 표시하고 사용자에게 요청한다.

1. 주제를 확정하고, 주제 선정 기준에 맞는지 점검한다. 어긋나면 짚는다.
2. 최근 글로 리듬을 보정한다.
3. **소스·팩트를 먼저 확보한다.** 코드·API·동작을 다루면 추측하지 말고 실제로 확인한다: 레포를 받아 파일을 읽거나, `deep-research` 등으로 출처를 모은다. 확인 못 한 주장은 쓰지 않는다.
4. **개요(목차 + 각 절 한 줄 요약)를 먼저 제시하고 합의**한다. 바로 본문을 쏟지 않는다.
5. 합의된 톤으로 작성한다. 사실·수치·소스는 확인된 것만 쓰고, 불확실하면 표시하거나 사용자에게 묻는다.
6. 긴 글은 절 단위로 나눠 작성하며 중간 점검을 받는다.

### 변환 모드 (초안 → 톤 적용)

1. 대상 파일을 확정한다.
2. **가장 두드러진 1~2단락을 먼저 변환**해 원본/수정안을 나란히 보여준다.
3. 피드백("이대로", "더/덜 강하게", "이 표현 빼")을 받아 나머지를 진행한다.
4. 변환은 **톤·리듬·형식만** 손본다. 사실·수치·코드·각주·API 이름은 바꾸지 않는다.

## 절대 규칙

1. 사실·수치·의도는 날조하지 않는다. 검증 안 된 수치·성능은 쓰지 않는다.
2. 변환 모드에서 의미를 바꾸지 않는다 (톤만 손본다).
3. 코드 블록, 표 셀, 각주, API 이름·경로·버전·측정값은 건드리지 않는다.
4. 한국어 전용이다. 영문 번역(.en.md)은 이 스킬 범위 밖이다.
5. 사용자 승인 없이 전체를 쏟아내지 않는다 (개요 합의 / dry-run 샘플 우선).
