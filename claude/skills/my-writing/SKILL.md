# 두 가지 톤으로 글쓰기

**블로그 게시용 톤(`blog`)**과 **기술 도서 톤(`book`)** 두 가지로 한국어 글을 쓴다. 새 글 작성과 기존 초안 변환을 모두 지원한다.

이 스킬은 자급자족적이다. 두 톤의 규칙은 아래에 모두 명문화되어 있으며, **외부 저장소나 특정 파일 없이도 동작한다.** 레퍼런스 저장소가 로컬에 있으면 보정에만 선택적으로 활용한다(아래 "선택적 보정" 참고).

## args

- `blog {주제 또는 파일경로}` — 블로그 톤
- `book {주제 또는 파일경로}` — 기술 도서 톤
- 입력이 **주제/개요 텍스트**면 생성 모드, **`.md` 파일 경로**면 변환 모드. 모호하면 어느 쪽인지 묻는다.
- 톤(blog/book)이 빠지면 둘 중 무엇인지 먼저 묻는다.

생성 모드의 기본 동작은 **개요 합의 후 작성**, 변환 모드의 기본은 **dry-run 샘플 후 승인**이다. 사용자 승인 전까지 전체를 쏟아내지 않는다.

## blog 톤 (블로그 게시용)

### 문체

> **2026-07 문체 전환**: 기존의 단정·직설 톤이 거만하게 읽힌다는 사용자 피드백으로 **겸손한 설명형**으로 전환했다. 2026-07 이전 글은 옛 톤이므로, 보정 소스로 읽을 때 리듬 차이에 주의한다.

- **종결어미**: `~다` 평어체. 차분한 설명형 리듬을 유지한다. 판정 선고형 단문("React가 이겼다.", "둘은 같은 사건이 아니다.")을 연달아 끊지 말고, 문장을 풀어서 쓴다.
- **단정 완화**: 의견·전망은 "~라고 생각한다", "~일 가능성이 높다", "~일 것이다" 수준으로 여지를 남긴다. 검증된 사실은 단정해도 된다. 확신의 근거가 본문에 있을 때만 세게 쓴다.
- **명령·권유형 지양**: "~보자", "기억해 두자", "갈라야 한다" 같은 독자 지시형 대신 "~를 보면", "~는 뒤에서 다시 나온다", "~할 필요가 있다"로 쓴다.
- **승부·도발 어휘 지양**: "판돈", "두들긴다", "선고", "완패" 같은 관용구와 냉소("훈훈한 이야기다")를 피한다. 위트는 절제하고, 겸손하되 비굴하지 않게.
- **서론**: 정의·배경으로 시작하지 않는다. **구체적 증상·사실·수치로 즉시 진입**한다. (예: "막상 쓰면 직관이 자꾸 빗나간다. DB 쿼리를 감쌌는데 쿼리는 여전히 두 번 나가고…")
- **고정 구조 금지** (2026-08-15 사용자 피드백): "먼저 결론" 절, "정리" 절 같은 정형 스캐폴드를 글마다 기계적으로 반복하지 않는다. 구조는 글의 성격에 맞게 그때그때 설계한다. 긴 글에 요약이 필요하면 서론 산문에 녹이거나 그 글에 맞는 자연스러운 제목·형태로 담고, 마무리도 볼드 키워드 불릿 틀 대신 산문 등 글에 맞는 방식을 택한다.
- **정직한 트레이드오프**: 과장하지 않는다. 반론과 자기 논거의 한계를 명시한다. ("~라는 것이 정직한 평가일 것이다")
- **용어 풀이**: 처음 나오는 개념은 괄호로 짧게 푼다. (예: "빌림 검사기(borrow checker, 참조의 소유권과 수명을 컴파일 타임에 강제하는 장치)")

### 형식

- **em dash(—) 금지**. 보충은 마침표로 끊거나 괄호로, 동격·부연은 콜론으로, 강조는 볼드로 처리한다. blog·book 양 톤 공통이다. 사용자가 자기 글에서 —를 쓰지 않기로 했으므로, 코드 주석·각주·인용 원제까지 포함해 전수 제거하고 `grep '—'`로 0개를 확인한다.
- **마크다운 링크 허용**. `[텍스트](경로)` 형태로 본문에 직접 건다.
- **헤딩 번호 없음**. `## 서론`, `## 먼저 결론`처럼 자유로운 제목.
- **분량 자유**. 하한 없음.
- `>` 인용구로 측정 환경, "한 문장으로:" 요약, 노트를 단다.
- 비교는 표로 정리하고, 키워드는 볼드로 강조한다.
- **요약 불릿을 쓰게 되는 경우**, 앞에 리드인 한 줄과 뒤에 마무리 한 줄을 두고, **불릿은 길이·구조를 일부러 들쭉날쭉하게** 둔다. 모든 항목을 "굵게 + 부연 + 짧은 마무리" 같은 동일 틀로 4개 찍어내면 AI 티가 난다.
- **"다룰 내용"·"목차" 같은 불릿 로드맵 절을 만들지 않는다.** 실제 글엔 없는 전형적 AI 패턴이다. 개요가 필요하면 서론 산문 안에 한 문장으로 녹인다.

### 근거 (blog도 엄격)

- 소스 코드는 직접 인용하고 **버전 태그를 고정**한다 (예: `v19.2.6` 태그). `main`은 인용하지 않는다.
- 측정값은 환경(머신, 버전, 도구)을 명시한다. 가상 수치·과장 성과 금지.
- 인용한 소스는 실제 파일과 대조해 확인한다.
- 소스 딥다이브 글은 **서론에 버전·범위 고지 `>` 블록**(고정 태그, 분석 시점)과 각주(`[^n]`)를 두고, 본문엔 파일명·식별자(예: `ReactCacheImpl.js`, `ReactSharedInternals.A`)를 구체적으로 박는다. "명세와 구현을 본다"는 선언만으로는 부족하다.

### 주제 선정 (생성 모드)

**"검색하면 바로 나오는 글"이 아니라 "이 글을 참고해야 답할 수 있는 글"**을 쓴다. "X vs Y" 비교글, "N가지 방법" 나열형, "~란 무엇인가" 단순 설명형은 피한다. 직접 해본 경험(성능 분석, 마이그레이션, 장애 분석), 프레임워크 내부 딥다이브, 실무 레퍼런스가 강점이다.

### 톤 예시 (이 리듬을 목표로 한다)

증상으로 여는 서론:

> `cache()`는 React 19에 정식 추가된 API다. 그런데 막상 쓰면 직관이 자꾸 빗나간다. DB 쿼리를 감쌌는데 쿼리는 여전히 두 번 나가고, 같은 코드를 클라이언트 컴포넌트로 옮겼더니 아무 일도 일어나지 않고, 인자를 객체로 바꿨더니 캐시가 통째로 안 먹는다.

단정을 완화한 의견 제시 (2026-07 이후 톤):

> 여기까지는 충분히 있을 법한 이야기다. 다만 한 가지 짚고 싶은 부분이 있다. 이 시나리오는 인과의 마지막 고리를 생략하고 있다. 검증은 읽을 수 있는 대상에만 가능하다. 낯선 스택으로 작성된 코드는 검수가 어려운 블랙박스가 되기 쉽고, 그런 코드를 책임지고 승인하기는 어렵다. 그래서 결국 자신이 읽을 수 있는 익숙한 스택을 선택하게 될 가능성이 높다.

구체적 현상으로 말하되, 판정을 선고하는 대신 근거를 펼쳐 놓고 결론은 "~할 가능성이 높다" 수준으로 닫는다.

### frontmatter (새 글 생성 시)

```yaml
---
title: '...'
tags:
  - ...
published: true
date: YYYY-MM-DD HH:MM:00
description: '...'
thumbnail: /thumbnails/YYYY/MM/{slug}.png
---
```

날짜는 사용자에게 확인하거나 오늘 날짜를 쓴다. 저장 경로는 사용자에게 확인한다.

## book 톤 (기술 도서)

### 문체

- **종결어미**: `~이다/~한다/~있다`. 1인칭 최소화, 3인칭 관찰자 시점.
- **균형잡힌 표현**: "반드시/절대"보다 "일반적으로/대부분의 경우"를 쓴다.
- **전문성과 접근성 균형**: 전문 용어는 첫 등장 시 **한글 용어(영문) - 쉬운 설명** 형식으로 풀고, 필요하면 비유를 병행한다.
- **문장 길이**: 한 문장은 2~3줄을 넘기지 않는다. 한 단락은 3~5문장, 하나의 핵심 아이디어만 담는다.
- **차분하고 정확하게**. 과장·위트보다 정확성과 객관성이 우선이다.

### 형식

- **em dash(—) 금지**. 보충은 마침표로 끊거나 괄호로, 동격·부연은 콜론으로, 강조는 볼드로 처리한다. 헤더·캡션의 구분도 콜론(`:`)으로 통일한다.
- **본문 마크다운 링크 금지**. 모든 출처는 각주(`[^n]`)로 단다. 각주는 문서 맨 끝 `---` 아래 번호순으로.
- **헤딩 번호 필수**. 점(.)으로 구분한다: `# 1.3`, `## 1.3.1`, `### 1.3.1.1`. 번호 끝에 마침표를 붙이지 않는다.
- **모든 제목 다음 1~2문장 인트로 필수**. 바로 코드·리스트로 시작하지 않는다.
- **절 끝 전환 문장**: 다음 절로 넘어갈 때 새 정보를 담은 전환 문장을 둔다(다음 제목을 풀어 쓴 반복은 금지). 다음 제목만으로 맥락이 충분하면 생략한다.
- **다이어그램은 mermaid**. ASCII art 다이어그램 금지.
- **거듭제곱은 유니코드 위첨자**(`2³⁰`). `^`, `<sup>`, LaTeX 금지. (코드 블록 안 `2 ** 30`은 그대로)
- 표는 열 3~4개로 제한하고, 표 앞에 소개 문장, 뒤에 핵심 포인트 문단을 둔다.

### 근거 (가장 엄격)

- 검증 가능한 사실만 쓴다. **모든 성능 수치·개선률은 출처(공식 문서/연구) 또는 직접 측정으로 뒷받침**한다.
- 구체적 수치에는 측정 환경과 방법을 명시한다("Node.js 24.x 환경에서 측정"). 일반 범위 제시("일반적으로 30~70%")는 허용.
- 가상 수치·과장 성과 금지. AI 생성 콘텐츠를 출처로 인용하지 않는다.
- 원문 인용은 `"원문"(한글 번역)[^n]` 형식으로 출처와 함께.

### 구조

서론·본론·결론을 반드시 갖춘다. 개념은 정의 → 배경/필요성 → 작동 원리 → 적용 → 한계 순으로 전개한다. 코드는 앞에 목적 설명(2~3문장), 뒤에 동작·트레이드오프 설명(1단락 이상)을 붙이고, 모든 코드 블록에 언어를 명시한다. 본문의 API·함수·변수·모듈명은 백틱으로 감싼다.

### 톤 예시 (이 리듬을 목표로 한다)

구체적 현상으로 열되 차분하게, em dash 없이:

> 빌드도 되고, 컨테이너도 뜨고, 요청도 정상적으로 처리된다. 하지만 `docker stop`을 실행하면 이상한 일이 벌어진다. 컨테이너가 즉시 종료되지 않고 정확히 10초를 기다린 뒤 강제로 끊긴다. `CMD npm start`라는 한 줄이 원인이다.

정의 후 단계적 전개, 용어는 괄호로 풀이:

> 컨테이너는 가상 머신이 아니다. 별도의 OS 커널을 실행하지 않으며, 호스트 커널 위에서 두 가지 리눅스 커널 기능을 조합해 프로세스를 격리한다. 첫 번째는 namespace다. namespace는 프로세스가 볼 수 있는 시스템 자원의 범위를 분리한다.

blog 톤과 같은 평어체지만 위트를 빼고, 한 문장은 짧게 끊는다.

## 한국어 표현 점검 (blog·book 공통)

> 2026-08에 8월 포스트 전수 검토에서 나온 실제 지적들을 규칙화한 것. 초안 작성 시 지키고, 퇴고 시 체크리스트로 쓴다.

### 기술 용어: 축자 번역도, 어색한 음차도 금지

- **영어 기술 관용어를 축자 번역하지 않는다.** 실제 지적 사례: layer→"겹", knob→"손잡이", (code) hygiene→"위생", copy→"부"(앱 한 부), cheap failure→"싼 실패", buys nothing→"돈이 사는 건 없다". 통용되는 음차(레이어, 스크레이프)나 자연스러운 우리말(설정값, 뒷정리, 비용이 거의 들지 않는)을 쓴다.
- **통용도 낮은 음차·반쪽 음차 금지.** 사례: 키잉(keying), 트라이(trie), 목(mock→"모의"), 랩(lab→"실험 환경"), 퍼-HPA(per-→"HPA별"), 노이즈 이웃(noisy neighbor→"시끄러운 이웃(noisy neighbor)"). 판단 기준은 "한국 개발자 글에서 흔히 보는 표기인가".
- **낯선 용어·비유어는 첫 등장에서 병기한다.** `백스톱(backstop, 안전장치)`, `함대(fleet, 서비스의 전체 파드 무리)` 식으로. 병기 없이 반복 사용하지 않는다.
- **한 글 안에서 같은 개념을 두 말로 부르지 않는다.** 사례: 같은 문단에서 "긁고"와 "스크레이프", 글 전반의 "처리량 천장"과 갑자기 등장하는 "cliff". 첫 등장에서 병기로 묶고 이후 하나로 통일한다.

### 번역투 문형 금지

- **무생물 주어 + 행위 동사**: "그 돈이 사는 건 아무것도 없다" → "그 돈으로 얻는 것은 아무것도 없다". "그 이야기는 짚으며 돌아온다" → "~할 때 다시 나온다".
- **독자를 "너"로 부르지 않는다**: "너는 노드 값을 낸다" → "돈은 노드 값으로 나간다".
- **영어 명사구 축자 나열 금지**: "단일 최고 레버리지 비용 절감" → "레버리지가 가장 큰 단일 비용 절감 수단".
- **부사+형용사 직역 금지**: "일부러 완전한 이미지"(deliberately complete) → "의도적으로 완전하게 만든 이미지".
- **부정의 위치**: "아무것도 바뀌었다고 느끼지 않는" → "아무것도 바뀌지 않았다고 느끼는". 부정은 종속절에 둔다.
- **논항 확인**: "프로세스에게 세계를 속이다"처럼 동사의 조사 구조가 어긋난 문장을 쓰지 않는다.

### 어휘·연어

- 헷갈리는 쌍: 반복 측정은 **횟수**(회수 아님), 정당한 이유는 **명분**(명목 아님), 형벌 은유는 **형(刑)**(행 아님).
- 관념어 지양 (2026-08-15 피드백): "층위" 같은 학술적 관념어를 쓰지 않는다 ("평소에 있어도 되는 층위" → "평소에는 서로 몰라도 되는 영역"). 사용자가 일상적으로 쓰는 말(영역, 부분, 지점)로 푼다.
- "처방" 금지 (2026-08-16 피드백): 해결책을 "처방"이라 부르지 않는다. "해법"으로 쓴다.
- 부사 중복 금지: "유일하게 고유하게" 같은 동의어 겹침.
- "아무 + 명사 + 가"는 비문: "아무 건강한 워커가" → "살아 있는 워커 중 하나가".

### 두 번 읽게 만드는 문장 금지

- **동음이의어 오독**: "실명"(失明/實名), "절도"("절 + 도"가 竊盜로 읽힘), "행"(行/刑)처럼 첫 독해가 갈리는 단어는 한자 병기, 어순 변경, 다른 단어로 회피한다.
- **수식 순서**: "죽은 직전 컨테이너" → "직전에 죽은 컨테이너". 수식어가 어디 걸리는지 한 번에 읽혀야 한다.
- **관계절 오독**: "**폭발 반경과 롤아웃 단위**가 작은 파드는~"처럼 볼드 리드가 뒤 문장의 주어에 붙어 읽히는 구조를 피한다.
- **은유는 첫 등장에서 세운다**: "실명 절이다"처럼 비유를 정의 전에 준기술용어로 쓰지 않는다. 비유가 깔리지 않은 글에서 다른 글의 은유를 가져오지 않는다.
- **압축 조어 금지**: "4동시" → "동시성 4". "p90에서 피크" 같은 중의적 결합은 "피크 시간대 실사용량의 p90"으로 푼다.

## 워크플로우

**입력 전제**: "직접 해봤다"류의 경험·실측 데이터는 AI가 만들 수 없다. 측정값·장애 경험·벤치마크가 필요한 글이면 **사용자가 제공한 데이터를 입력으로 받는다.** 없으면 그 자리를 지어내지 말고 비워둔 채 `[측정값 필요]`로 표시하고 사용자에게 요청한다.

1. 톤(blog/book)과 주제를 확정한다. blog면 주제 선정 기준에 맞는지 점검하고, 어긋나면 짚는다.
2. 선택적 보정 소스가 있으면 참고한다(없어도 진행).
3. **소스·팩트를 먼저 확보한다.** 코드·API·동작을 다루면 추측하지 말고 실제로 확인한다: 레포를 받아 파일을 읽거나, `deep-research` 등으로 출처를 모은다. 확인 못 한 주장은 쓰지 않는다.
4. **개요(목차 + 각 절 한 줄 요약)를 먼저 제시하고 합의**한다. 바로 본문을 쏟지 않는다.
5. 합의된 톤으로 작성한다. 사실·수치·소스는 확인된 것만 쓰고, 불확실하면 표시하거나 사용자에게 묻는다.
6. 긴 글은 절 단위로 나눠 작성하며 중간 점검을 받는다.

### 변환 모드 (초안 → 톤 적용)

1. 톤(blog/book)과 대상 파일을 확정한다.
2. **가장 두드러진 1~2단락을 먼저 변환**해 원본/수정안을 나란히 보여준다.
3. 피드백("이대로", "더/덜 강하게", "이 표현 빼")을 받아 나머지를 진행한다.
4. 변환은 **톤·리듬·형식만** 손본다. 사실·수치·코드·각주·API 이름은 바꾸지 않는다.

## 절대 규칙

1. 사실·수치·의도는 날조하지 않는다. 검증 안 된 수치·성능은 쓰지 않는다.
2. 변환 모드에서 의미를 바꾸지 않는다 (톤만 손본다).
3. 코드 블록, 표 셀, 각주, API 이름·경로·버전·측정값은 건드리지 않는다.
4. 외부 저장소·파일에 의존하지 않는다. 위 명문화된 가이드만으로 완결적으로 동작한다.
5. 한국어 전용이다. 영문 번역(.en.md)은 이 스킬 범위 밖이다.
6. 사용자 승인 없이 전체를 쏟아내지 않는다 (개요 합의 / dry-run 샘플 우선).
