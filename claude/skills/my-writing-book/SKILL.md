# 기술 도서 톤 글쓰기

기술 도서 톤으로 한국어 글을 쓴다. 새 글 작성(생성 모드)과 기존 초안 변환(변환 모드)을 모두 지원한다.

**공통 규칙**: 전역 `my-writing` 스킬(한국어 표현 점검·em dash 금지)을 항상 함께 적용한다. 이 스킬은 book 톤 고유 규칙만 담는다.

## args

- `{주제 또는 파일경로}` — 입력이 **주제/개요 텍스트**면 생성 모드, **`.md` 파일 경로**면 변환 모드. 모호하면 어느 쪽인지 묻는다.

생성 모드의 기본 동작은 **개요 합의 후 작성**, 변환 모드의 기본은 **dry-run 샘플 후 승인**이다. 사용자 승인 전까지 전체를 쏟아내지 않는다.

---

## 문체

- **종결어미**: `~이다/~한다/~있다`. 1인칭 최소화, 3인칭 관찰자 시점.
- **균형잡힌 표현**: "반드시/절대"보다 "일반적으로/대부분의 경우"를 쓴다.
- **전문성과 접근성 균형**: 전문 용어는 첫 등장 시 **한글 용어(영문) - 쉬운 설명** 형식으로 풀고, 필요하면 비유를 병행한다.
- **문장 길이**: 한 문장은 2~3줄을 넘기지 않는다. 한 단락은 3~5문장, 하나의 핵심 아이디어만 담는다.
- **차분하고 정확하게**. 과장·위트보다 정확성과 객관성이 우선이다.

## 형식

- **em dash(—) 금지** — 상세 규칙은 전역 `my-writing` 스킬 참고. 헤더·캡션의 구분도 콜론(`:`)으로 통일한다.
- **본문 마크다운 링크 금지**. 모든 출처는 각주(`[^n]`)로 단다. 각주는 문서 맨 끝 `---` 아래 번호순으로.
- **헤딩 번호 필수**. 점(.)으로 구분한다: `# 1.3`, `## 1.3.1`, `### 1.3.1.1`. 번호 끝에 마침표를 붙이지 않는다.
- **모든 제목 다음 1~2문장 인트로 필수**. 바로 코드·리스트로 시작하지 않는다.
- **절 끝 전환 문장**: 다음 절로 넘어갈 때 새 정보를 담은 전환 문장을 둔다(다음 제목을 풀어 쓴 반복은 금지). 다음 제목만으로 맥락이 충분하면 생략한다.
- **다이어그램은 mermaid**. ASCII art 다이어그램 금지.
- **거듭제곱은 유니코드 위첨자**(`2³⁰`). `^`, `<sup>`, LaTeX 금지. (코드 블록 안 `2 ** 30`은 그대로)
- 표는 열 3~4개로 제한하고, 표 앞에 소개 문장, 뒤에 핵심 포인트 문단을 둔다.

## 근거 (가장 엄격)

- 검증 가능한 사실만 쓴다. **모든 성능 수치·개선률은 출처(공식 문서/연구) 또는 직접 측정으로 뒷받침**한다.
- 구체적 수치에는 측정 환경과 방법을 명시한다("Node.js 24.x 환경에서 측정"). 일반 범위 제시("일반적으로 30~70%")는 허용.
- 가상 수치·과장 성과 금지. AI 생성 콘텐츠를 출처로 인용하지 않는다.
- 원문 인용은 `"원문"(한글 번역)[^n]` 형식으로 출처와 함께.

## 구조

서론·본론·결론을 반드시 갖춘다. 개념은 정의 → 배경/필요성 → 작동 원리 → 적용 → 한계 순으로 전개한다. 코드는 앞에 목적 설명(2~3문장), 뒤에 동작·트레이드오프 설명(1단락 이상)을 붙이고, 모든 코드 블록에 언어를 명시한다. 본문의 API·함수·변수·모듈명은 백틱으로 감싼다.

## 톤 예시 (이 리듬을 목표로 한다)

구체적 현상으로 열되 차분하게, em dash 없이:

> 빌드도 되고, 컨테이너도 뜨고, 요청도 정상적으로 처리된다. 하지만 `docker stop`을 실행하면 이상한 일이 벌어진다. 컨테이너가 즉시 종료되지 않고 정확히 10초를 기다린 뒤 강제로 끊긴다. `CMD npm start`라는 한 줄이 원인이다.

정의 후 단계적 전개, 용어는 괄호로 풀이:

> 컨테이너는 가상 머신이 아니다. 별도의 OS 커널을 실행하지 않으며, 호스트 커널 위에서 두 가지 리눅스 커널 기능을 조합해 프로세스를 격리한다. 첫 번째는 namespace다. namespace는 프로세스가 볼 수 있는 시스템 자원의 범위를 분리한다.

평어체지만 위트를 빼고, 한 문장은 짧게 끊는다.

## 워크플로우

**입력 전제**: "직접 해봤다"류의 경험·실측 데이터는 AI가 만들 수 없다. 측정값·장애 경험·벤치마크가 필요한 글이면 **사용자가 제공한 데이터를 입력으로 받는다.** 없으면 그 자리를 지어내지 말고 비워둔 채 `[측정값 필요]`로 표시하고 사용자에게 요청한다.

1. 주제를 확정한다.
2. 선택적 보정 소스가 있으면 참고한다(없어도 진행).
3. **소스·팩트를 먼저 확보한다.** 코드·API·동작을 다루면 추측하지 말고 실제로 확인한다: 레포를 받아 파일을 읽거나, `deep-research` 등으로 출처를 모은다. 확인 못 한 주장은 쓰지 않는다.
4. **개요(목차 + 각 절 한 줄 요약)를 먼저 제시하고 합의**한다. 바로 본문을 쏟지 않는다.
5. 합의된 톤으로 작성한다. 사실·수치·소스는 확인된 것만 쓰고, 불확실하면 표시하거나 사용자에게 묻는다.
6. 긴 글은 절 단위로 나눠 작성하며 중간 점검을 받는다.

### 변환 모드 (초안 → 톤 적용)

1. 대상 파일을 확정한다.
2. **가장 두드러진 1~2단락을 먼저 변환**해 원본/수정안을 나란히 보여준다.
3. 피드백("이대로", "더/덜 강하게", "이 표현 빼")을 받아 나머지를 진행한다.
4. 변환은 **톤·리듬·형식만** 손본다. 사실·수치·코드·각주·API 이름은 바꾸지 않는다.

---

## 절대 규칙

1. 사실·수치·의도는 날조하지 않는다. 검증 안 된 수치·성능은 쓰지 않는다.
2. 변환 모드에서 의미를 바꾸지 않는다 (톤만 손본다).
3. 코드 블록, 표 셀, 각주, API 이름·경로·버전·측정값은 건드리지 않는다.
4. 한국어 전용이다.
5. 사용자 승인 없이 전체를 쏟아내지 않는다 (개요 합의 / dry-run 샘플 우선).
